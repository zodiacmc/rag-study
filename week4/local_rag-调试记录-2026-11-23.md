### 问题 3：Embedding 大批量入库报 400，tokenize 端口拒绝连接（✅ 已规避）

#### 现象

`Chroma.from_documents → add_texts` 阶段，POST `/api/embed` 返回 **400 Bad Request**，底层报错：

```
Post "http://127.0.0.1:<随机端口>/tokenize": dial tcp 127.0.0.1:<端口>:
connectex: No connection could be made because the target machine actively refused it. (status code: 400)
```

#### 排查过程（分层对照实验）

| 实验组 | 请求方式 | 结果 |
|---|---|---|
| 单条 curl `/api/embed` | 仅 input | ✅ HTTP 200 |
| `ollama stop bge-m3` 重置 runner 后单条 curl | 仅 input | ✅ 200 |
| Python `ollama.embed` 单条 | 仅 input | ✅ OK |
| Python `ollama.embed` 300 条 | 仅 input | ✅ OK（直连 SDK） |
| 同上，带 `options(temperature/top_k)` | 带 options | ❌ tokenize 端口拒绝 |
| 同上，`keep_alive=None` | 无 options | ✅ OK |
| `options` 全为 `None` | 带 options | ❌ 失败 |
| `OllamaEmbeddings.embed_documents` 300 条 | langchain 封装 | ❌ 复现失败 |
| 模块级 `ollama.embed` vs `Client` 实例方法 | 同 300 条 | 模块级成功、实例方法失败，两者源码相同 |
| 10 次连续 300 条重试 | — | 约 50% 失败，失败有聚集性，`ollama stop` 清理无效 |
| 批量 10 / 30 / 100 条，各 20 次 | 小批量 | ✅ 全部成功 |
| 批量 300 条 | 大批量 | ❌ 约 50% 失败 |

#### 根因（最终结论，修正早期误判）

**Ollama 0.40.17 服务端 runner 在 tokenize 阶段的缺陷：批量过大时（实测 300 条）触发；批量 ≤100 条稳定成功。**

- 早期曾误判为「请求体带 `options` 字段触发」，后经对照实验推翻：`options` 是否携带与失败无关，当时的相关表现是大批量失败交替分布造成的巧合。
- 与 `keep_alive`、请求参数也无关；`ollama stop` 重启 runner 不能根治。

#### 规避方案（已落地）

子类化 `OllamaEmbeddings` 为 `SafeOllamaEmbeddings`：

- `batch_size = 50`：文本拆成每批 ≤50 条逐批请求；
- `max_retries = 3`：单批失败有限重试；
- `retry_interval = 0.5`：重试间隔 0.5 秒；
- 打印总条数、批次数与每 10 批进度。

> 若日后升级 Ollama 服务端，可重新压测大批量请求；确认 bug 消失后再考虑去掉分批逻辑。

### 问题 6：检索命中两条「id 不同、内容相同」的重复片段（✅ 已修复）

#### 现象

调试时断点观察到：向量库里两条记录 **id 不一样、内容却完全相同**，检索时会同时命中，引用列表出现一模一样的两段。

#### 排查过程（分层定位：入库重复 → 分块重复 → 源文本重复）

1. **查库**：总条数 855，按内容去重统计只有 580 条——275 组内容各重复了 2 次。
2. **判断是否重复入库**：元数据只有 `source`，无法区分；纯本地复现分块（不依赖 Ollama），发现分块器本身就切出了这 275 组重复。
3. **查源文本**：重复 chunk 在源 txt 中出现于位置 **48494** 和 **185365**（相距约 13.7 万字符），两处上下文一模一样（合同编第四百六十五条起的大段）。即该段文本在 `中华人民共和国民法典_20200528.txt` 里**真实存在两份**，很可能是当初 docx → txt 转换时把同一段抽取了两次（或 docx 内有重复文本框/节）。

#### 根因（两点叠加）

1. **源文本大段重复** → 分块器切出 275 组内容完全相同的 chunk（855 块里 580 块不同，275 组各重复 2 次）；
2. **入库未指定 `ids`**：`langchain_chroma` 不指定 ids 时自动生成 **uuid**（不是内容哈希），所以同内容也会得到不同 id，看起来「id 不同、内容一样」。

#### 处理（已落地）

- **分块后、入库前按内容去重**：用 `set` 记录已见 `page_content`，重复的 chunk 不再入库；日志打印 `去重：855 → 580 个 chunk（移除 275 个）`。
- **删除旧库重跑**：旧 `chroma_local` 仍是含重复的 855 条，受「非空则复用」逻辑影响不会自动刷新，已清空 `chroma_local` 后重新入库去重后的 580 条（分 12 批）。

> 源头未治理：`week2/out_text` 这批 txt 的生成脚本为什么把合同编那段写了两遍，仍需回查；其他文件可能也有同样的转换重复，建全量库前建议先批量统计重复率。

### 小插曲（ℹ️ 非阻塞）

- `ollama` Python 包没有 `__version__` 属性，`Client` 也没有 `version()` 方法，直接查询会抛 `AttributeError`；服务端版本最终通过 `/api/version` 查到为 0.40.17。

## 五、可复用的排查思路

1. 先区分是封装层问题还是服务端问题：裸 SDK / curl 直连 vs langchain 封装对照。
2. 小批量 → 大批量梯度压测，定位是否为批量压力触发。
3. 对照不同参数（options、keep_alive）逐个排除，避免被偶发交替失败误导成参数问题。
4. 失败率/聚集性用多次循环统计，不要凭一两次重试下结论。
5. 服务端类问题先查版本号，再判断是本地代码缺陷还是环境 bug。
6. 检索出现重复片段时，按「入库重复 → 分块重复 → 源文本重复」逐层排除：先统计库内内容去重数，再纯本地复现分块，最后回源文本查重复出现次数与位置。
